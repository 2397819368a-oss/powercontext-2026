# 记仇酒馆 · 一个真的记得你的酒馆老板

> **赛道**：Dify × PowerContext
> **一句话**：用 Dify 编排对话流程，用 PowerContext 做跨会话长期记忆，
> 让一个本地小模型演活一个「记仇、认账不认脸」的酒馆老板——
> 你三天前在这儿赊的那碗酒，他下一轮还在记着。

---

## 1. 它解决什么问题

绝大多数「AI NPC」的长期记忆是假的：系统提示词里塞一段固定人设，或者把最近几轮对话截断留在上下文里。
一旦**开新会话**，它就失忆了。

这个作品要解决的是：**让 NPC 记性跨轮、跨会话成立，并且每一句引用的旧账都能被验证是真从记忆库里翻出来的。**

## 2. 成品形态

「漏雨酒馆」老板老陈，52 岁，走镖出身，右手背有疤，口头禅「人可以穷，账不能糊」。
跟他的每一次互动都会决定他对你的**信任度（-5…+5）**，而信任度会被写回记忆，
影响下一次他用什么语气跟你说话。

```
账本：信任度 1（本轮变化 +1）· 翻到旧账 6 条
本轮记下：阿七还清了欠的一碗酒钱

记忆回响 —— 老陈这次翻到的是：
1. [state]   老陈对旅人阿七的当前态度：信任度 0（生客），欠一碗酒钱没结
2. [episode] 三天前的雨夜，阿七把桌上的醋当成酒喝了一大口……没付钱
3. [rule]    酒馆规矩：生客先付钱再上酒，熟客可以赊
```

回答里永远带着「这次翻到了哪几条记忆」，**不是让模型自述「我记得你」，而是把引用亮出来**。

## 3. 技术分工

| 组件 | 承担什么 | 为什么必须是它 |
|---|---|---|
| **Dify 1.18.0**（Chatflow） | 全流程编排：检索 → 拼 prompt → 生成 → 解析 → 写回 | 赛题必选；节点化让「记忆怎么进 prompt」是**可见的**，不是黑盒 |
| **PowerContext 1.4.1** | 长期记忆的存储与混合检索（FTS + 向量 + RRF）、scope 隔离 | 它的定位就是「跨会话携带上下文」；单 scope 即一个存档 |
| **llama.cpp + Qwen2.5-3B-Instruct** | 演老陈，输出台词 | OpenAI 兼容接口，可一键替换成任何更强的模型 |
| **multilingual-e5-small（ONNX）** | 本地 embedding | 让 PowerContext 的**向量通道**真正可用（见 §5） |

```
玩家输入
   ↓
Dify Chatflow
   ① HTTP   → PowerContext /v1/memory/search      （把玩家这句话拿去翻账本）
   ② 代码   → 拼「你记得的事」+ 读出上一次的信任度
   ③ LLM    → 老陈开口（强制 JSON 输出 reply / trust / memory）
   ④ 代码   → 解析 JSON + 裁剪信任度 + 生成待写回的一句话
   ⑤ HTTP   → PowerContext /v1/memory/remember    （写回，下一轮/下次会话都能翻到）
   ⑥ 回答   → 台词 + 账本状态 + 记忆回响
```

节点数 8，连线 7，全部由 `app/dsl/grudge-tavern.chatflow.yml` 描述，一键导入。

第 ⑤ 步的模型输出确实是当轮生成的 JSON，而不是事后编的。

关键 checkpoint：

| 考察点 | 证据 |
|---|---|
| 记忆真的持久化 | `PowerContext 写入 +1`，三轮 → 9→10→11→12 |
| 同会话能召回 | 第 2 轮没提伞字，老陈自己说出了「蓝色油纸伞」 |

| 检索走了向量 | 节点输出显示 `mode=hybrid`（配 embedding 前是 `text`） |
| 输出结构化可控 | `解析: json`，`trust` 被钳在 -5…5 |

## 5. 最有价值的一个工程结论：不配 embedding，记忆就是残废

这是本作品里最重要的一次返工，也是我认为对别人最有用的经验。

PowerContext 的 Memory 检索有两条通道——**全文**和**向量**——混合时用 RRF 融合。
但是：**没配 embedding 供应商时，向量通道根本不存在**，`search` 返回的 mode 是 `text`。

而全文通道的准入规则是（源码 `powercontext/builtin/artifacts/search.py`）：
查询先 Jieba 分词、去停用词，然后要求候选**至少覆盖 2 个不同的查询词**
（`_FTS_MIN_MATCHED_TERMS = 2`）。于是：

| 玩家说什么 | 账本里存着什么 | 全文通道的结果 |
|---|---|---|
| 「我的**蓝色油纸伞**呢」 | …把**蓝色油纸伞**落在柜台… | ✅ 命中，词条重合 |
| 「我是不是有**东西**落这儿了」 | 同上 | ❌ **零个实词重合，候选被准入规则直接刷掉** |

也就是说：**只用全文检索的话，玩家越「说人话」，NPC 越像失忆。**
这不是 PowerContext 的缺陷，是我们没给它语义检索的能力。

**修法**：本机起一个 OpenAI 兼容的 embedding 服务
（`deploy/embed_server.py`，multilingual-e5-small 的 ONNX 导出，
自己做 masked mean pooling + L2 归一化），然后在 `pc-config/powercontext.env` 里配上：

```ini
POWERCONTEXT_SERVER_INFERENCE_EMBEDDING_BASE_URL=http://127.0.0.1:8091/v1
POWERCONTEXT_SERVER_INFERENCE_EMBEDDING_MODEL=openai:multilingual-e5-small
POWERCONTEXT_SERVER_INFERENCE_EMBEDDING_PROFILE_ID=e5-small-local
POWERCONTEXT_SERVER_INFERENCE_EMBEDDING_DIMENSION=384
POWERCONTEXT_SERVER_INFERENCE_EMBEDDING_NORMALIZATION=unit
```

配完 `/health/ready` 出现 `"inference.embedding":"ready"`，
`search` 的 mode 从 `text` 变成 **`hybrid`**，上面第 2、3 轮才成立。

配之前 vs 配之后，`tools/dify-smoke.mjs` 的结果是 **7 passed / 2 failed → 9 passed / 0 failed**。

## 6. 另外两个踩出来的坑

**① 写回格式会反噬召回质量。**
早期把「玩家原话 → 老陈台词」整句回灌进记忆。结果同一个问题问第二次时，
检索结果被上一轮的**回声**占满，真正要找的旧账被挤到第 3、4 位。
现在只存第三人称摘要 + 信任度，短且关键词密集。

**② 3B 小模型不会听「请按格式输出」。**
第一版要求模型输出 `<回应>/<信任度>/<记住>` 三段标签，实测直接失败：
它要么只吐一句台词，要么把 few-shot 示例的台词原样照抄。
改成 llama.cpp 的 **JSON Schema 约束解码**（`response_format`）后才稳住——
结构不可能错，模型只能决定内容。温度从 0.7 降到 0.5 后，表达的稳定性也明显改善（8/9 → 稳定 9/9）。

**还试过一个反向的坑**：为了让它「用物件本名回答」，我加了一条跟验收问法几乎一样的
few-shot 示例，同时把温度压到 0.2。结果三轮输出**一字不差地照抄示例里的「蓝布包袱」**，
稳态掉到 7/9，比不加还差。小模型会把 few-shot 退化成复读——示例教的是行为，它学成了答案。
最终只保留一条**不同场景**的示例（还酒钱），「必须说本名」放在文字规则里约束。

## 7. 怎么复现

全部流程脚本化了，不需要在界面里手点：

```bash
# ① 本机三个服务（前两个的权重与二进制需自行下载，见 RUNBOOK §2）
cd C:/llama && ./llama-server.exe -m C:/gguf/qwen2.5-3b-instruct-q4_k_m.gguf \
  --host 127.0.0.1 --port 8088 -c 4096 -t 8 --no-warmup

.venv-embed/Scripts/python.exe deploy/embed_server.py --port 8091

POWERCONTEXT_HOME="C:/pc-data-vec" \
  .venv/Scripts/powercontext.exe server run --env-file pc-config/powercontext.env

# ② Dify（源码需自行 clone，见 RUNBOOK §5）
cd ../dify-source/docker
cp <本仓库>/dify/deploy/docker-compose.override.yaml ./docker-compose.override.yaml
bash <本仓库>/dify/deploy/pull-images.sh && docker compose up -d

# ③ 初始化 + 导入 + 模型注册 + 发布
cd <本仓库>/dify/app
export POWERCONTEXT_SERVER_AUTH_TOKEN=<你自己填的那个 token>
node seed/seed-demo.mjs
node tools/dify-bootstrap.mjs        # 建管理员 / 清旧应用 / 注入 scope+token / 导入 / 发布 / 取 Key
node tools/dify-setup-model.mjs      # 装 OpenAI-API-compatible 插件并注册本地模型

# ④ 验收
node tools/dify-smoke.mjs            # 9 passed, 0 failed
```

> 仓库里的工作流 DSL 用 `REPLACE_WITH_YOUR_PC_SCOPE` / `REPLACE_WITH_YOUR_PC_TOKEN`
> 占位（导出时 HTTP 节点的 Bearer 值会明文落进 YAML），`dify-bootstrap.mjs`
> 会在导入前用本机真值替换掉，不需要手工改 YAML。

完整的踩坑清单（含每个报错的原文和解法）见 `app/docs/RUNBOOK.md`：
- `8080` 被联想 `ApplicationWebServer.exe` 占用导致 llama-server exit 1
- 容器访问宿主机被 Dify 的 SSRF 代理拦（`SSRF_PROXY_ALLOW_PRIVATE_IPS`）
- `cr.weaviate.io` 在 WSL2 的 daemon 里解析不了（override 换镜像源）
- Dify 1.18 登录要 **base64 密码** + Cookie/CSRF 双头
- Service API 只跑**已发布**的工作流（`Workflow not published`）
- 给已存在的库追加 embedding 配置会触发 `incompatible_schema`（要换 HOME 从头初始化）

## 10. 诚实说明（限制与边界）

1. **模型只有 3B。** 同样的召回，它可能说「那把蓝色油纸伞」，也可能只说「你落的东西」。
   把温度降到 0.5 之后三组测试稳定通过，但更强的模型会显著更好——
   替换方式只是改 Dify 里的模型配置，链路不用动。
2. **没有用 seekdb。** 赛题允许 seekdb / PowerContext 二选一，我们选 PowerContext
   因为它承担的是「记忆」这个核心玩法。另外嵌入式 seekdb 只支持 Linux/macOS，
   本机是 Windows，PowerContext 落到了 SQLite 后端。
3. **信任度由模型裁决。** 代码侧做了钳制（-5…5）和缺失兜底，但一次幻觉仍可能改错一格。
4. **单 scope = 单存档。** 多人同时玩会串账；`node seed/seed-demo.mjs --fresh` 可重置。
