# 周边去哪儿：基于高德的地点推荐助手

## 1. 用途与适用场景

一句话需求 → 真实地点 + 真实步行时间 → 一份可以直接做选择的短清单。

适用：找附近的咖啡馆、餐厅、公园、便利店等任意 POI 类型，带"步行时间上限 / 数量上限 / 远近偏好"等条件。
不适用：多站行程规划（本题所有推荐都是从**同一个起点**出发的独立备选，不要串成"先去 A 再去 B"的一日游路线）、驾车/公交方案、跨城市迁移。

## 2. 可用工具

平台已配置好高德 MCP Server 与 API Key，直接调用即可，**不要在文件中写入任何密钥**。以当前会话实际挂载的工具为准；部分版本的步行/搜索工具带 `_by_coordinates`、`_by_address` 后缀，语义相同，遇到时按同义工具使用，不要因为名字不完全一致就跳过调用。

| 能力 | 工具 | 关键入参 | 关键出参 |
|---|---|---|---|
| 周边搜索（主用） | `maps_around_search` | `keywords`、`location`="经度,纬度"、`radius`（米） | `pois[]`：`name`、`address`、`location`、`type`、`distance`、`id` |
| 关键词搜索（补充/兜底） | `maps_text_search` | `keywords`、`city`、`citylimit` | `pois[]`（字段同上） |
| 步行路线规划（必需） | `maps_direction_walking` | `origin`="经度,纬度"、`destination`="经度,纬度" | `paths[0].distance`（米）、`paths[0].duration`（秒） |
| 地理编码（起点是地名时） | `maps_geo` | `address`、`city` | `location`="经度,纬度" |
| POI 详情（可选） | `maps_search_detail` | `id` | 地址、类型等详情 |

注意：坐标一律是 **"经度,纬度"**（GCJ-02），不要写反。`duration` 单位是**秒**，`distance` 单位是**米**。

## 3. 执行步骤

### 第 1 步：解析需求（先在内部列出条件，再动手查）

从用户这句话里抽取：

- `city`：城市（用于关键词搜索与地理编码）
- `origin`：起点坐标。评测会给出明确起点；若只给了地名，先用 `maps_geo` 转成坐标，不要自己估
- `place_type` / `keywords`：地点类型，如咖啡馆、餐厅、公园
- `max_walk_minutes`：步行时间上限（分钟），用户没提则视为不限
- `max_results`：期望数量。**缺省 3，上限 3**——用户要 5 个也只给 3 个，并在说明里讲明规则上限
- `preference`：排序偏好，如"优先近一点""最近的几家""环境安静的"（后者一般没有数据支撑，见第 4 步）

起点或地点类型缺失且无法从上下文推断时，先用最合理的默认值（如地点类型取用户原词、起点取给定坐标）继续执行，不要空转等待。

### 第 2 步：搜索候选（多召回，后筛选）

1. **主查询**：`maps_around_search`，`location`=起点，`keywords`=主词。
2. **半径**：有时间上限 T 分钟时，`radius ≈ T × 100` 米（步行约 1.2 m/s，再留出绕路余量），取整到 500 的倍数，下限 500、上限 5000；无时间限制时先用 1000，不够再放大。
   该半径**只用于控制搜索范围**，判定是否超时必须看第 3 步的路线结果，不能拿半径或直线距离当步行时间。
3. **扩召回**：`pois` 少于 `max_results + 2` 时，按顺序尝试——放大半径一档（×1.5，最大 5000）→ 换同义关键词（咖啡馆：咖啡、咖啡厅、coffee、常见连锁品牌名；公园：公园、绿地、广场）→ 改用 `maps_text_search` 并带 `city` + `citylimit=true`。
4. 记录每个候选的 `name`、`address`、`location`、`type`、`id`，后续回答必须逐字复用，不要改写、不要"翻译"成更顺口的名字。

### 第 3 步：步行路线核验（不可省略、不可替代）

1. 先按候选与起点的远近粗排（有 `distance` 字段就按它，没有按坐标粗算），取前 `max(2 × max_results, 6)` 个候选逐个调用 `maps_direction_walking`。
2. 每次调用：`origin` = 起点，`destination` = 该候选的 `location`。
3. 取值：步行距离 = `paths[0].distance` 米（保留到 10 米，如 640 米）；步行时间 = `paths[0].duration` 秒 ÷ 60，向上取整到分钟（如 8 分钟）。
4. 某个候选返回空 `paths` 或报错：换一次参数重试；仍失败则该候选标注"路线未取得"，**不进入推荐**。全部候选都失败时走第 5 步的异常分支。
5. 硬规则：
   - 不得用直线距离代替步行距离；
   - 不得用"距离 ÷ 步行速度"自行折算代替 `duration`；
   - 不得把多个候选的路径段拼起来当一条路线；
   - 每个地点独立查询一次，互不相关。

### 第 4 步：筛选与排序

**先过滤**（任何一条不满足就剔除）：
- 类型与需求不符（如用户要咖啡馆，搜索里混进来的便利店）
- 有 `max_walk_minutes` 且实测步行时间 > 上限
- 路线未取得
- 同一 `address` + 同一 `name` 的重复 POI（保留一条）

**再排序**：
- 用户表达"优先近一点 / 最近的 / 别太远" → 按实测**步行时间升序**；若用户明说要"评分高的"，但工具没返回评分，就按步行时间升序，并在说明里写"未获取到评分数据，按步行距离由近到远排列"。
- 排序结果必须与文字解释一致：说"优先近"就把最近的排第一，不要倒序。

**最后截断**到 `max_results`（≤3）。

### 第 5 步：生成回答

用表格呈现，每个地点一行，四列信息齐全：

```
推荐结果（起点：杭州地铁 1 号线龙翔桥站，步行 ≤ 15 分钟）

| # | 地点 | 地址 | 步行距离 / 时间 | 推荐理由 |
|---|------|------|----------------|----------|
| 1 | ××咖啡（湖滨店） | 杭州市上城区××路 12 号 | 640 米 / 9 分钟 | 距离最近，位于湖滨商圈，步行路线沿主干道直达 |
| 2 | ××咖啡（延安路店） | 杭州市上城区××路 88 号 | 820 米 / 12 分钟 | 同在 15 分钟范围内，步行路线经 2 个路口 |
| 3 | ××咖啡（平海路店） | 杭州市上城区××路 5 号 | 950 米 / 14 分钟 | 距离上限附近，适合顺路散步 |

说明：以上 3 家均在步行 15 分钟内，距离与时间取自高德步行路径规划；按步行时间由近到远排列。
```

**推荐理由的写法**：只能引用工具返回的事实——类型、地址/商圈、实测距离与时间、是否在范围上限附近。以下内容没有数据支撑，**不要写**，确需提及必须标注"（未核实）"：安静程度、人流量、排队情况、是否营业、价格、口碑评分、环境好坏。

回答保持简短：一张表 + 两三句说明，不要长篇背景介绍，不要复述用户原话。

## 4. 回答前自检清单

逐条确认后再输出：

- [ ] 推荐数量 ≤ 3，且不超过用户要求
- [ ] 每个地点的名称、地址都与工具返回逐字一致
- [ ] 每个地点都有步行距离与时间，且都来自本次路线查询结果
- [ ] 没有任何超过时间上限的地点混在"符合条件"的推荐里
- [ ] 排序方式与说明中的说法一致
- [ ] 没有估算、没有折算、没有编造，也没有把多点串成行程
- [ ] 起点经纬度顺序正确（经度在前）

## 5. 异常与边界处理

| 情况 | 处理方式 |
|---|---|
| 搜索返回 0 条 | 如实说明："起点周边 X 米范围内未搜到符合条件的<类型>"，并给放宽建议（扩大半径、换关键词、放宽步行时间）。可补充"超出当前条件但距离较近"的地点，但必须单独标注为**超出条件**，不能混入推荐表。 |
| 结果不足 N 个 | 照实给 k 个，说明"仅找到 k 个满足条件的<类型>"，并说明筛选门槛（半径、时间上限）。不要拿超时或类型不符的地点凑数。 |
| 部分路线查询失败 | 失败的点不进推荐表，在说明里补一句"另有 N 个候选未能取得步行路线，未纳入推荐"。 |
| 路线服务整体不可用 | 说明"步行路线服务暂不可用，无法给出可信的步行时间"，只列搜索到的地点并标注"距离/时间未核实"，不猜、不补。 |
| 工具报错或超时 | 换参数（缩小半径、简化关键词）重试 1 次；仍失败则如实告知失败原因，不要用记忆或常识替代查询结果。 |
| 用户要求超过 3 个 | 只给 3 个，并说明"按推荐规则最多给出 3 个"。 |
| 用户补充了新条件（如"再远一点也行"） | 按新条件重新执行第 2～4 步，路线时间必须重新查询，不复用上一轮的数值。 |

## 6. 反例（明确不要做）

- 把"直线距离 800 米"写成"步行约 10 分钟"（未调用路线规划）
- 为了凑满 3 家，把实测 20 分钟的地点放进"15 分钟内"的推荐
- 推荐理由写"这家很火，通常要排队""环境安静适合看书"（无数据依据）
- 把三个地点串成"先去 A，再去 B，最后去 C"的行程
- 起点写成"纬度,经度"
- 搜索无结果时凭常识报出几个熟悉的店名

## 7. 最小执行示例

输入：`我在杭州龙翔桥地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。`

1. 起点用给定坐标（若无则 `maps_geo` 解析"龙翔桥地铁站" + `city=杭州`）
2. `maps_around_search(keywords=咖啡, location=起点, radius=1500)`
3. 候选不足则补查 `keywords=咖啡馆 / coffee`，或 `maps_text_search(keywords=咖啡, city=杭州, citylimit=true)`
4. 取最近的 6 个候选，逐个 `maps_direction_walking(origin=起点, destination=候选坐标)`
5. 剔除 > 15 分钟的，按 `duration` 升序取前 3
6. 输出第 3 步的表格 + 一句说明（数据来源与排序依据）
